## 一、喜马拉雅（参考：`喜马拉雅/`）

### P0-1 · 96K 档位映射错误导致静默降级

- **证据**：`core/ximalaya_download_manager.py:230-235` 写 `'96K': 2`，注释断言 "level 2 and level 96 currently resolve to the same 96K M4A"；同一文件 `:2552-2557` 却写 `'96K': 96`，`:2866` 又硬编码 `/96`。
- **参考实测**（`喜马拉雅下载接口分析.md:65-83`）：`/0` → ~24.8kbps；**`/1` `/2` → `-aacv2-48K.m4a`**；`/3` 起才是 96K，且 `/3`~`/10` 返回同一文件。
- **后果链**：`:2304-2307` 生成降级链 `[2, 96]` → 第一发 `level=2` 拿到 48K 即成功 → `:2415-2451` 把标签记为 `"96K"` → **用户以为下了 96K，实际 48K，且文件名写着 96K**。
- **改法**：档位语义收敛为单一常量，三处引用同一来源：
  ```python
  LEGACY_REDIRECT_CHAIN = {'96K': (3, 1, 0), '64K': (1, 0), '48K': (1, 0), '24K': (0,)}
  MIN_ACCEPT_KBPS = {'96K': 80, '64K': 40, '48K': 40, '24K': 18}
  ```
  并在 `os.replace()` 落盘前用已有的 `_m4a_duration_seconds()`（`:1853-1890`）反算实测码率，不达标记为 `quality_unavailable` 走下一档，而非当成功；标签写**实测值**。

### P0-2 · 网络错误被当作降级信号（legacy 路径）

- **证据**：`core/ximalaya_download_manager.py:2343-2354` 对**任何**非 200 都 `continue` 降级，含 502/503/504；`:2454-2461` 的 `except Exception` 也降级。
- **参考做法**（`ximalaya_dl.py:113-118,431-464`）用互斥异常区分语义：
  ```python
  class PermissionDenied(Exception):  # 真没权限 → 可降级
  class TransientError(Exception):    # 网络瞬时错误 → 原地重试，绝不降级
  ```
  文档 `:223-232` 记录代价：初版误判导致「**537 集里 31 个文件被静默降级**」。
- **本项目内部不一致**：`:894-921` 的 V4 路径**做对了**（`if self.last_error_type != "quality_unavailable": break`，注释写明网络/权限失败必须可见）。
- **改法**：抽 `XIMALAYA_RETRYABLE_STATUS = {429,500,502,503,504,522,524}` 与 `XIMALAYA_PERMISSION_STATUS = {400,401,403,404,410}`，**降级只在 permission 类发生，重试只在 transient 类发生**。并发 8~12 时 502 是高频事件，触发概率远高于权限错误。

### P0-3 · 完全未处理 `ret=726`（立即购买畅听）

- **证据**：`grep 726 core/ximalaya*.py` **零命中**（已复核）。`:2365-2396` 的 JSON 分支只认 `ret == 130`；726 落到通用错误分支，靠 `:250-254` 的 `permission_words` 文本匹配「购买」二字**偶然命中**——依赖服务端文案不变。
- **参考做法**（`ximalaya_dl.py:256-279`）：读响应体前 400 字节，解析 JSON，`ret==726` 直接抛 `PermissionDenied("立即购买畅听")`。726 是付费集无权限的权威信号，比 `isFree`/`isAuthorized` 可信。
- **改法**：显式加分支 + 错误码常量表：
  ```python
  XIMALAYA_RET_PERMISSION = frozenset({726})
  XIMALAYA_RET_NOT_M4A = frozenset({130})
  ```
  `_record_error` 的 `restricted` 判定改为 `status_code in (401, 403, 726)`，不再依赖文案。

### P1-4 · `playPathAacv224` 码率标注自相矛盾

- **证据**：`:2857` 注释写 "实际是64kbps"、键名 `M4A_64`；`:1902` 却标 "公开 AAC 24K"；`core/ximalaya_manager.py:578` 把它的 `level_fix` 设为 `96`。
- **参考实测**：`playPathAacv224` → `/0` → **24K**；`playPathAacv164`/`playUrl64`/`downloadUrl` → `/1` → **48K**。文档 `:77-81` 专门警告「**字段名有误导性，不要按字段名推断码率**」。
- **改法**：建立字段→档位的**单一事实源**表，三处改为引用；`level_fix` 由 96 改 0。

### P1-5 · 仍在使用已下线的接口

- **证据**：`core/ximalaya_download_manager.py:2928` 请求 `https://www.ximalaya.com/revision/play/v1/audio?...`，且该方法被 `:2797` 无条件调用，每次取流都产生一次注定 404 的请求 + 最长 10s 超时。
- **参考实测**（文档 `:27`）：该接口返回 **404 (`Server: CW`)，取流接口已下线**。同理 `core/ximalaya_manager.py:881,1436` 用的 `getTracksList` 实测返回 `{"ret":407,"msg":"webtk缺失"}`。
- **改法**：删除 `_get_pc_audio_urls`；`getTracksList` 从 `fetchers` 首选链移出或加 `ret==407` 短路标记。

### P1-6 · 长度校验用 80% 容差，弱于参考的精确比对

- **证据**：`:733`（web 路径）与 `:1737`（V4 主路径）都是 `total_size < int(expected_size * 0.8)`；而 `:2420`（legacy）与 `:2070`（公开兜底）用的是精确比对——**同一文件三套强度**。
- **参考做法**（`ximalaya_dl.py:282-328`）：先写 `.part` 再原子改名，`got != expected` 即删文件抛 `TransientError`。文档 `:208-219` 记录价值：逐字节核对发现 **2 集被 CDN 静默截断**（本地 4.95MB / 服务端 16.80MB），「连接提前 EOF 却不抛异常」。
- **改法**：抽统一 `_verify_download_size()`（精确比对 Content-Length 与声明 fileSize + 最小 8KB 下限），四处复用。若担心历史 `fileSize` 不准，改为**连续两次不符才判失败**，而不是放宽到 80%。

### P1-7 · 容器类型按字段名硬编码

- **证据**：`:1898` `audio_format = 'MP3' if source_field in ('playUrl64','playUrl32','downloadUrl') else 'AAC'`。
- **参考做法**：不假设，**从 URL 后缀与文件头双向判定**（`ximalaya_dl.py:251-253` `ext_of_url`、`:331-346` `is_valid_audio` 嗅探 `ID3`/`ftyp`/帧头）。新专辑上 `playUrl64` 指向 `.m4a`，硬编码会把 m4a 标成 MP3。
- **改法**：`:1898` 改为下载完成后用文件头嗅探生成标签；`download_worker.py:124-137` 已有「下载后纠正后缀」机制，复用即可。

### P1-8 · `device=android` 硬编码且无回退

- **证据**：`:2816` 硬编码单一 device；而同项目 `core/ximalaya_manager.py:539-570` 有 `for device in ('ios','www2','android')` 回退循环，注释直指「**android 常返回 924，并非真下架**」。
- **参考实测**（文档坑 1）：UA 用浏览器 → `mobile/v1/album` 返回空壳、`album/track` 返回 `{"ret":924,"msg":"该内容因故已下架"}`；且 `device=iPhone` 即使配 iOS UA 也返回 924，**只用 Android 这套**。
- **改法**：`:2816` 复用 manager 已验证的回退顺序，抽共享常量 `XIMALAYA_BASEINFO_DEVICE_ORDER`。

### P1-9 · `_get_web_audio_urls` 不解密，把 AES 密文当 URL

- **证据**：`:2893-2922` 注释自承「这里应该解密 URL，但为了简化测试，我们直接使用」；而**正确实现已存在于同项目** `core/ximalaya_manager.py:465-537`（`_decrypt_audio_url_aes` + `_decrypt_audio_url_xor`）+ `:457-463` `_is_valid_cdn_url`。
- **后果**：未解密密文经 `:2805` 混入总表，可能被选中并下载失败。
- **改法**：复用既有解密函数；更优是删除 `_get_web_audio_urls`/`_get_pc_audio_urls`，四路合并式取流（`:2790-2810`）改为**按优先级顺序尝试、成功即返回**。

### P1-10 · 搜索端点全部无风控签名头

- **证据**：`core/ximalaya_manager.py:2139-2193` 三个端点（`m-revision/page/search`、`revision/search/main`、`revision/search`）**均未带签名头**；`:2246-2247` 注释显示已知风险但未解决。
- **参考结论**（`喜马拉雅元数据与搜索接口.md:41-96`）：`xm-sign = browserId && sessionId`，**伪造会被服务端静默识别，返回空结果**；PC 端返回 `{"ret":200,"data":{"reason":"risk invalid","riskLevel":5}}`。
- **改法**：无法解决签名，但要**把静默失败变可见** —— 照搬参考的 `describe_search` 思路（`ximalaya_meta.py:319-351`）：命中 `recommendItems` 非空但 `albumViews.albums` 为空 → 判定为被风控，记 WARN 并在 UI 标注降级状态；区分 `ret=303 needLogin` 与真的无结果。

### P2-11 · 缺 HTTP Range 断点续传

- **证据**：全仓 `grep "Range'\|bytes="` 零命中；`.part` 在重试时被 `unlink`（`:2334`、`:2020`），已下载字节全部丢弃。
- **参考做法**（`ximalaya_dl.py:403-410`）：已存在且 >1KB 的文件自动跳过；`--repair` 按序号前缀定位后原地覆盖。
- **注意**：CDN 直链由 `buy_key+sign+timestamp+token` 签名、**每次请求实时生成且有时效**（文档 `:85`）。因此 Range 续传只在**单次任务内的重试**有效，跨会话需重新取链。

### P2-12 · 缺本地音质体检闭环

- **证据**：`:1853-1890` 的 `_m4a_duration_seconds()` 已能读 mvhd，`:1892-1909` 的 `_public_quality_label()` **已经算了实测码率却只用于拼标签**；`download_worker.py:166-173` 的品质标记只认三种，无法表达「应 96K 实得 48K」。
- **参考做法**（`ximalaya_dl.py:470-514`）：按 `MIN_KBPS` 阈值分「达标/低码率/损坏」三类，出体检报告；`:529-564` `do_repair` 比对集列表后原地覆盖重下。最终「体检达标 2115/2115」。
- **改法**：新增 `verify_local_quality(directory, expected_quality)`，供订阅周期性自检。**这是让 P0-1/P1-6 类问题早期显形的手段。**

### 保留项（不要回退）

本项目在**架构强度**上多处强于参考实现：V4 签名构造（`:1081-1140`，复刻 Android TreeMap + URLEncoder 语义）、AES+XOR 双重解密（`:149-211`）、**x-tk 本地票据生成**（`core/ximalaya_local_ticket.py:87-167`，参考实现完全没有）、限流冷却机制（`:120-147,334-368`）、权限 fail-closed 判定（`:1806-1851`）。

## 二、懒人听书（参考：`懒人听书/`）

### P0-1 · `tempToken` 签名算法错误 → 短信登录已失效

- **参考报告直接点名**（`逆向分析报告.md` §8.2「与 AudioFlow 实现的差异（重要修正）」），并给出实测记录：
  ```
  sc 仅算空参数       → status=483 请求验证失败
  sc 不含 sc 参数     → status=483 请求验证失败
  sc 含 meta+公共参数 → status=0  ✅ 返回 token（49 字符）
  ```
- **证据（已复核）**：

  - `core/lrts_manager.py:356` —— `params={"sc": calc_sc(path, {}), "meta": meta}`：**只对空参数签名**，且请求无 `imei/nwt/q/mode`。
  - `core/lrts_manager.py:366`（AutoRegister 兜底）—— `calc_sc(path, {"meta": meta})`：算了 `meta`，**仍漏公共参数**。
  - 对照 `:337` 的 `_signed_params()` —— 那才是正确写法。
  - 影响：`lrts_send_sms_code`（`:727-734`）与游客态 `_client_or_guest`（`:818-822`）都拿不到 token。

- **为什么测试没抓到**：`tests/test_lrts_login.py:32` 把 `fetch_temp_token` mock 掉了 —— 测试替身掩盖了签名错误。
- **改法**：两处统一改为 `self._signed_params({"meta": meta})`；补一个**不打桩真实签名输入**的单元测试（断言 `sc` 由 `meta` + 公共参数共同决定）。

### P0-2 · 节流闸门按「章」而非按「请求」

- **证据**：`_throttle_audio_request()` 全项目**只在一处调用**（`:1151`，每章入口）；而码率降档探测循环 `:520-523` 内的 3~4 次 `getListenPath` 是**连发无节流**，`LrtsAppClient.get`（`:340-344`）内部也没有闸门。
- **参考做法**（`lrts_dl.py:189-199`）：把闸门放在 `call()` 内，**每个 HTTP 请求都过闸**；并发建议 `--jobs 2`，内建 `status=114 下载过于频繁` 的自适应退避（起始 0.5s，连续 4 次成功降 0.2s，遇 114 立刻 ×1.8 上限 8s）。
- **报告明确警告**（§0/§6）：这正是撞 `status=114` 风控的写法。
- **改法**：把限速下沉到 `LrtsAppClient.get/post` 内部；`status=114` 时自适应加长间隔。

### P1-3 · 默认档位是 HQ(3)，且下载链路不透传界面音质

- **证据**：`core/lrts_manager.py:71` `DEFAULT_AUDIO_QUALITY = 3`；`download_worker.py:988-990` 未透传；`tests/test_lrts_manager.py:309` 还把 `quality=3` **固化成断言**。
- **参考做法**：`quality` 语义 `normal=1, high=2, hq=3, sq=4`（对应 Android `ResQualityLevel`），README 明确「目标是最高码率」。
- **后果**：**即便 VIP 也永远请求不到 SQ=4**。
- **改法**：默认提到 4 并让 `get_chapters(..., quality=)` 透传；同步改测试断言（`tests/test_lrts_manager.py:309` 是会踩的测试）。

### P1-4 · 专辑章节无 V2 兜底

- **证据**：`:483-489` 只走 App 接口；无 `trackId` 的章节才走老接口 `/yyting/gateway/getListenPath.action`。
- **参考做法**（`reverse/接口路径映射_167条.txt:53`）：`getAblumnAudiosV2.action` 亦可。
- **改法**：`getAblumnAudios.action` 失败时回退 `…AudiosV2.action`；并注意 App 接口游客态返回 **482 请登录**，需回退 `www.lrts.me/ajax/book/…`（参考 README 实测表）。

### P1-5 · 章节字段缺 `resId` / `tme_id`，`is_paid` 阈值偏宽

- **证据**：`:1058,1074` 组装的章节 dict 缺这两个字段；`:1067` 的 `is_paid` 判定用 `> 0`。
- **参考**（`逆向分析报告.md` §2）：`getListenPath` 需要 `entityType, entityId, trackId, opType=1, quality, effect, section, resId`；`is_paid` 参考实现用 `> 1`。
- **改法**：补齐字段；`is_paid` 阈值改为 `> 1`。

### P1-6 · 专辑搜索是死代码

- **证据**：`search_album` 中 `:904-910` 有一个 `break` 使后续分支不可达。
- **参考**：`/yyting/search/searchAlbum.action`（专辑）与 `/yyting/bookclient/BookSearch.action`（书籍）两个接口都可用。
- **改法**：修死代码或删掉无用分支。

### P1-7 · `sc` 依赖 `self._last_path` 实例状态，存在线程竞态

- **证据**：`:320` 存 `_last_path`，`:336` 在 `_signed_params` 里读它，`:341/347` 在 `get/post` 里写它 —— 多线程下 A 线程可能在 B 线程改写后再签名。
- **改法**：`_signed_params(path, business)` 改为显式传 path 参数，去掉实例状态。

### P1-8 · 落盘无 `.part` 与残留清理

- **证据**：`:1213-1235` 直接写目标文件；叠加 `download_worker.py:935-943` 的「存在且 >1024 字节即跳过」判据。
- **后果**：中断产生的半截文件会被**误判为已完成**。
- **改法**：`.part` + 原子改名（参考 `ximalaya_dl.py:282-328` 同款）。

### P2-9/10/11

- 补 `--probe` 等价物（只请求一集并打印真实 `url/quality/bitrate/mimeType/fileSize`），用于验证权限而不浪费整轮下载。
- 滑块：`_slider_required`（`:688-692`）只认 `460`，而实测 `getVerifyCode` 返回 **`status=2 请做滑动验证校验`**（§8.3），现在靠 msg 文本兜底才没暴露 → 补 `status=2` 判定。
- `_quality_ceilings` 每线程一份不共享（`download_worker.py:689-707`）→ 提升为进程级，避免重复探测。

## 三、酷我听书（参考：`酷我听书/kuwo-tingshu-dl/`）

> 这一组对比最有价值：两边是同一平台的独立实现。参考实现已被工程化为标准 Python 包。

### P0-1 · 分页 `rn=24`，而实测上限是 100

- **证据**：`core/kuwo_manager.py:51` `self._page_size = 24`（`已复核`）；`core/enhanced_search_manager.py:1298` 用 `get_chapters(..., page_size=10000)` 拉整本。
- **参考实测**（`work/re/API_INVENTORY.md:59`）：`rn` 上限 **100**，给 500/1000 也只回 100 条。
- **后果**：10000/24 = **417 个 API 页**，参考实现同场景只需 100 页。
- **改法**：改常量即可（`:373`/`:496` 都引用 `self._page_size`），加 env 逃生阀。

### P0-2 · 直链缺 `format=mp3`，且档位链含不存在的档

- **证据（已复核）**：`:644` 构造的 URL **无 `format` 参数**：
  ```
  mobi.kuwo.cn/mobi.s?f=web&user=1008611&source=...&type=convert_url_with_sign&rid={rid}&br={br_param}
  ```
  `:559/:571/:584` 用 `[320,192,128]` 三次请求试探；`:631-632` 的 `192kmp3` **不在 APK 逆向出的 14 个档位表内**。
- **参考实测**（`kuwo_dl/config.py:69-89`）：
  ```
  br=2000kflac            -> ogg/100k      br=2000kflac&format=mp3 -> mp3/128k
  br=128kmp3              -> aac/100k      br=128kmp3&format=mp3   -> mp3/128k
  ```
  即**不钉 `format` 会掉到 ogg/aac 容器**。
- **改法**：URL 加 `&format=mp3`；档位链改为参考的三元组 `(br 参数, format 参数, 接受条件)`；删 `192kmp3`。**收益：1224 集专辑的直链请求从约 4896 次压到约 2448 次。**

### P1-3 · 未读 `hasLossless`，白白探测 FLAC

- **证据**：`:511-520` 章节 dict 无 `hasLossless`；全项目 grep 只命中无关文件。
- **参考做法**（`client.py:371-384` + `config.py:104`）：`hasLossless=True` 时 `br=2000kflac` 才可能返回 FLAC，否则直接跳过无损探测（省 1/3 直链请求）。
- **改法**：章节解析时保留 `hasLossless`，据此决定是否探测无损。

### P1-4 · HTTP 层三条路径零重试

- **证据**：`_fetch_single_page`（`:263-292`）、`_get_download_url_internal`（`:650`）、`search_books`（`:170`）全部单次尝试；失败页只在 `:441-443` 串行重抓 1 次，**无退避、无 504 特判**。
- **参考做法**（`client.py:90-120`）：`MAX_RETRIES=5`；400/401/403/404 不重试；**502/503/504 退避 2.0s 起步**（注释：「酷我网关的常见过载响应，连续拉分页时容易出现」），其余 0.6s；加随机抖动。
- **旁证**：参考实现 `ACCEPTANCE.md:195` 记录的唯一失败样本正是**目录接口连续 5 次 504**。
- **改法**：抽统一 `_request()`，全链路复用。

### P1-5 · 限速器应独立化，且 sleep 不能放在 worker 线程内

- **证据**：`:389-390`/`:426-427` 两处 `time.sleep(self._page_request_interval)`，**都在 worker 线程内** → 3 并发时实际间隔只有 `0.15/3 = 0.05s`，限速形同虚设；搜索/直链/下载完全无节流。
- **参考做法**（`client.py:28-44`）：线程安全 `RateLimiter`（持锁维护 `_next`）；**API 与媒体下载用两个独立限速器** —— 注释实测「用 API 的间隔去卡下载会把吞吐压下来」。
- **改法**：`core/download/rate_limiter.py`（可跨平台复用）。

### P1-6 · 主动删除 `.part`，无断点续传

- **证据**：`:732-735` **主动 `os.remove(temp_path)`** 后 `wb` 重写；`grep Range|bytes=` 零命中。
- **参考做法**（`client.py:453-506`）：量已有 `.part` 大小 → `Range: bytes=N-` → 206 则 `mode="ab"` → 416 视为已完成。
- **后果**：酷我 FLAC 单集实测可达 **316MB**，中断即全丢。
- **改法**：加 Range 续传。

### P1-7 · API 字段裸用 `int()` / `//`，脏字段会静默清空结果

- **证据**：`:195-196` `int(album.get('PLAYCNT', 0))` / `int(album.get('musiccnt', 0))` 裸转；`:509-510` 的 `duration > 0` 与 `//` 若 `duration` 是字符串则 `TypeError`。

- **参考做法**（`client.py:509-513`）：`_int(v, default=0)` 兜底，9 处调用。
- **改法**：加 `_int()`；并把 `:215/:529` 的宽 except 改为**抛出** —— `core/enhanced_search_manager.py:1312-1314` 已有「失败必须可见」的同类注释可复用语义。

### P1-8 · 完整性校验缺 ffprobe 时长判据

## 四、云听 FM（参考：`云听/`）

### P1-1 · 搜索在枚举错误路径（参考实现已用铁证放弃）

- **证据**：`core/yuntu_manager.py:171-178` 硬编码 6 条候选路径循环探测（`/listening/listenSearch`、`/search/listenSearch`、`/search/search`、`/search/content`、`/search/all`）；`core/enhanced_search_manager.py:573-582` 在关键词搜索时直接调用。
- **参考结论**（`搜索接口分析报告.md:186-200`）：真实路由已挖出（`search/search/findSearchResourceList` 等），直接请求返回「网关拦截GET参数验签错误」而非 404 → 挂在**易盾网关**后；`Libsig` 由 `libsecexe.so` 在 native 层用设备信息生成，**静态不可复现**；枚举 976 个 `/web/` 搜索路径均 404。报告 §7.5 给出三通道结论表。
- **参考的替代方案**（可直接照搬）：走 **ytapi 无签名通道** `/interactive/getCategoryDetail` 拉全站清单建本地索引（实测 4.2MB / 13874 条），再用本地模糊匹配 + 播放量排序。
- **改法**：删除候选路径枚举，改为本地索引搜索；索引不存在时**明确提示「需先建索引」**，而不是给出误导性的空结果日志。

### P1-2 · `app_sign` 与官网算法不符

- **证据**：主签名 `md5_sign`（`:42-49`）**是正确的**（`.upper()` + `sorted` + `&timestamp=&key=`）；但 `app_sign`（`:51-65`）是另一套 —— 用另一个 key、**不排序**、**不含 timestamp**、对值做 `quote()`、且 `hexdigest()` **不带 `.upper()`**。
- **参考做法**（`yunting_api.py:20-21,39-44`）：`sign = MD5(参数按 key 排序拼接 + '&timestamp=' + 毫秒时间戳 + '&key=' + KEY).upper()`。
- **改法**：`app_sign` 唯一用途是调用已被证实不可用的搜索接口 → **直接删除**（连同 `_request_json` 的候选循环）。一个未经验证的签名函数配合必然失败的接口，最容易误导后续维护者。

### P1-3 · 请求头不完整（三处重复）

- **证据**：`:294-300`（`get_album_detail`）与 `:536-542`（补拉）**正确**给出 `equipmentId/platformCode/timestamp/sign` 四件套；但 `_request_json`（`:71-76`）只设 `User-Agent` 与 `Accept`，**`sign` 塞进 query、缺三个头** —— 即使路径正确也会验签失败。
- **附加坑**（参考 §7.3）：`/web/` 网关对**单参数**请求有特殊行为，必须「路径与 query 同时携带同一参数」：
  ```
  ?albumId=X        → data:null
  /X                → 验签错误
  /X?albumId=X      → ✅
  ```
  本项目 `:276` 满足"路径+query 同值"，但参数名用 `id` 而参考用 `albumId` —— **参数名不一致是风险**。
- **改法**：抽统一 `_signed_get(path, params)`，替换三处重复代码（`:279-300`、`:424-442`、`:527-542`）。

### P1-4 · 硬编码占位元数据污染用户文件

- **证据（已复核）**：`:356,391` 两处：
  ```python
  'albumTitle': data.get('albumTitle', '精神的力量'),
  'author': data.get('author', '中央广播电视总台'),
  ```
  另有 `:347/:382` 直接 `print` 完整接口响应、`:341` 打印构造的 URL。
- **参考做法**（`yunting_dl.py:437-456`）：缺失字段统一输出 `'-'`，绝不填看起来真实的常量。
- **后果**：接口缺字段时写入**看起来真实但与内容无关**的专辑名/作者，进入文件名与元数据（不可逆）。
- **改法**：兜底返回 `None`/`'-'`；`print` 改为 `logger.debug`（项目已有 `core/safe_logging.py`）。

### P2-5/6/7/8

- **后缀硬编码**：`core/download_worker.py:881-882` 对云听硬编码 `file_extension = '.mp3'`，而 `playUrlHigh` 可能是 m4a/AAC → 改为 `guess_ext_from_url(url)`（参考 `yunting_dl.py:184-192` `pick_ext`）。
- **音质档**：`:608` 固定 `playUrlHigh or downloadUrl`，无低档、无 quality 参数 → 抽 `_pick_url(single, quality)` 并透传。
- **错误处理吞异常**：`_request_json`（`:77-83`）`except Exception: print(...); return None` → 定义 `YuntuApiError(code, message, path)`，**区分「验签/参数不合法」（不可重试）与「5xx/超时」（可重试）**。参考 `yunting_dl.py:226-250` 直接 `raise RuntimeError(f"接口返回错误 code=... message=...")`。
- **死占位函数**：`get_audio_url()`（`:648-676`）打印提示后 `return None` → 删除或改为返回章节里的 `mediaUrl`。

### 保留项

### 顺带修掉的 7 个既有失败（已完成）

`tests/` 里 9 个失败中有 7 个与业务无关，根因是 **`mock.patch.dict(sys.modules, ...)`
的反模式**：`unittest.mock` 退出时会 `clear()` + `update(原始快照)`，把 patch 期间
新导入的模块一并移除。而 pycryptodome 的 `AES.new(key, MODE_ECB)` 是函数内延迟
import `Crypto.Cipher._mode_ecb`，其 raw lib 装载没有幂等缓存，被移除后重新导入
会二次 `ffi.cdef` 同名符号，抛：

```
cffi.FFIError: multiple declarations of function ECB_start_operation
```

表现为「先跑 A 文件、再跑 B 文件」时出现 4~7 个与密码学无关的失败
（网易云扫码、喜马拉雅解密），单独运行每个文件却都通过。
已用 `tests/support.py` 的 `patched_module()` 精确替换目标键，替换
`test_netease_qr_login.py` 与 `test_web_startup.py` 两处调用。

### 附带发现：源码权限问题

改造中发现 **322 个文件是 `000` 权限**（含 `README.md`、`requirements.txt`、
`Dockerfile`），属主为 `root`。而 `Dockerfile` 以 `USER audioflow` 运行、
`COPY --chown` **只改属主不改 mode** → 容器内非 root 进程读不了这些文件，
会在 import 阶段直接抛 `PermissionError`，启动即失败。

已在 Dockerfile 补上：

```dockerfile
RUN chmod -R a+rX /app
```

（参考实现 `DEPLOYMENT-VERIFY.md` 记录过同类事故：静态资源权限导致接口 500。）
