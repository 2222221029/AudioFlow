## 一、P0-1：PC 端取流链路（最大缺口）

### 缺口证据

- 全仓 `grep -E "download/v2/track|device=win32"` 在 `core/` 下**零命中** —— AudioFlow 根本没有 PC 端取流通道。
- 唯一的 PC 相关代码是 `core/ximalaya_manager.py:2966` 的 `_get_pc_audio_urls`：裸调 `https://www.ximalaya.com/revision/play/v1/audio?id=&ptype=1`，**不带任何签名头**；而源项目实测该接口已 **404 下线**（`Server: CW`）。它还被 `:2797` 无条件调用，等于每次取流都白白产生一次注定失败的请求（含最长 10s 超时）。
- `core/ximalaya_manager.py:85` 的 `self.xm_sign` 是一个**零引用的静态死串**（全仓没有任何地方读取它）：
  ```python
  # 添加xm-sign字段（从参考文件中获取）
  self.xm_sign = 'D256Y2bWKF5J/mrAkYx/IDBCUgI24xpXXFQE/gVJsU8b0X8a&&ptVWBRvUjLUvn9O8cP3uP9oALcOgOAzk0FOvKOLMRkM_1'
  ```
  也就是说，PC 端**签名能力完全不存在** —— 不是"签名过期"，而是"从来没有过"。注释「从参考文件中获取」也说明它当初是照抄进来的。本项目另有多处注释声明所调接口「无需 xm-sign」（`:818/:871/:960/:1037`），是对这个缺口的绕行。

### 源项目的对应实现

| 组件 | 位置 | 内容 |
|---|---|---|
| 取流端点 | `platforms/ximalaya/source_pc.py:264-266` | `GET https://mobile.ximalaya.com/mobile/download/v2/track/{trackId}/ts-{ms}?trackId=&device=win32\|darwin&trackQualityLevel={0..3}` |
| 必需头 | 同上 L270 | `xm-sign`（必需）+ Cookie 必含 `1&_token` 与 `1&_device`（缺后者 → `ret=2004`） |
| 签名常量 | `crypto.py:176-186` | `PC_SE` = mac/win/default 三套 AES key；`PC_CE` = 12 字符 IV 前缀；`PC_APP_KEY = "0zpnlXAG"` |
| 签名算法 | `crypto.py:243-268` | `plain = f"{trackId}{device}{ts后4位}{suffix}"`，`iv = (iv_prefix + ts后4位)`，AES-128-CBC/PKCS7 → base64url（**无 `=`、无换行**） |
| **签名生成** | `sign.py:110-145` | **纯 Python 复刻 dws SDK 降级算法**，产出 66 字符 `_2` sessionId |
| 档位语义 | `source_pc.py:18-20` | 0=24K、1=64K、2=128K HQ、3=256K 标称无损（实际档以响应 `downloadQualityLevel` 回传为准） |
| 地址解密 | `source_pc.py:310-316` | `data.downloadAacUrl` 是 base64url 密文，用**同一个** web ECB key 解密 |

### 为什么这一项价值高于预期：`xm-sign` 不再需要浏览器

源项目 README 早先的口径是「需要一次 Chromium 取 sessionId 后缓存复用」，但 `sign.py`（16:01 更新，晚于 README）**已经把它变成了纯 Python**：

```
明文 32 字节 = 8位随机hex + 4位base36随机 + 8位base62毫秒时间戳
             + base32标志位 + suffix(201/202) + 8位CRC32
密文 = AES-128-CBC(明文, key=iv="y3hbnr8d4s2ztjbca1wgxk6mqktf9pxr"[:16], PKCS7) → 48B
输出 = urlsafe_base64(密文) + "_2"  → 64+2 = 66 字符
```

支撑它的实测结论（`sign.py:4-30`，四组可控变量对照）：

| 组 | browserId | sessionId | 结果 |
|---|---|---|---|
| A | 真 | 真 | 通过（基线） |
| B | 真 | 随机 | 失败 `ret=-1` 风控 |
| C | **随机** | 真 | **通过** ← browserId 根本不校验 |
| D | 随机 | 随机 | 失败 |

且 CDP 阻断上报端点 `hdaa.shuzilm.cn` 后 SDK 走降级路径产出的 `_2` 签名**同样通过校验** → sessionId 是本地算法产物，不依赖服务端。

**对本项目的意义**：AudioFlow 为了拿真机票据已经引入了 `bridge/frida_client.py` + `bridge/agents/ximalaya.js`（Frida 桥）。PC 端这条路**完全不需要 Frida、不需要 Node、不需要 Chromium** —— 只要把 `sign.py` 的那 7 个纯标准库函数搬过来即可。

### 落地要点

1. 需要新增的常量：`PC_SE`（mac/win 两套，default 与移动端相同可复用）、`PC_CE`（mac/win 两套 12 字符前缀）、`PC_APP_KEY="0zpnlXAG"`、`SESSION_AES_KEY`。
   - 注意 `PC_SE["default"]` 与 `MOBILE_SIGN_KEY_HEX` **是同一套**（`crypto.py:404-407` 有自检断言），所以移动端已有的常量可以直接复用一半。
2. 需替换掉 `ximalaya_manager.py:85` 的硬编码签名（改为一处生成、可缓存）。
3. 签名可高频复用：源项目实测**一次签名连用 10+ 次**（PC 报告），40 分钟后仍有效；建议缓存 TTL 6 小时（`sign.py:45`）。
4. 踩坑：Base64 末尾若带 Android `URL_SAFE` 的 `\n`，拼进 query 会变成 `sign=...%0A`，服务端在权限校验之前就返回 `ret=1001`（`crypto.py:249-251`）。务必 `urlsafe_b64encode` 后 `.rstrip("=")` 且校验无空白。

## 二、P0-2：扫码一次 → 三端通用凭证

### 缺口证据

- `core/ximalaya_qr_login.py:187-188` 的 `get_cookies()` 返回**浏览器 cookie 字典**（20+ 个外围 cookie），没有派生任何 pc/mobile 凭证。
- 同文件 `:46-47` 的 `session_id = str(uuid.uuid4())`、`browser_id = md5(uuid4())` **形态是错的**：真机 browserId 是 36 字节 → 48 字符标准 base64；真机 sessionId 是 66 字符的 AES 产物。这两个值目前没被用于签名，但说明该路径尚未接通签名体系。
- `core/ximalaya_credentials.py` 有移动端 ticket 的解析/状态/合并（`normalize_ximalaya_mobile_credentials`、`ximalaya_mobile_credential_status`），但**没有「从一个 token 派生出三端凭证」的能力**。

### 源项目的对应实现

核心是 `platforms/ximalaya/auth.py:389-437` 的 `universal_credentials()`，实跑输出（本次验证，token 用占位值）：

```
web_cookie    = 1&_token=<UID>&<HEX>
pc_cookie     = 1&_token=<UID>&<HEX>; 1&_device=win32&<UUID>&4.0.15
mobile_cookie = 1&_device=android&<UUID>&9.4.52; 1&_token=<UID>&<HEX>;
                channel=and-d12; impl=com.ximalaya.ting.android;
                osversion=33; device_model=V2059A; url_verify_mode=1
mobile_ua     = ting_9.4.52(V2059A,Android33)
mobile_headers= {x_tk: <本地签发>, cookie, user_agent, api_device: android2,
                 host: mobile.ximalaya.com, device: android}
```

### 为什么能通用（源项目的决定性实验）

| 要素 | 能否本地派生 | 说明 |
|---|---|---|
| `1&_token` | ❌ 必须登录拿 | **账号级主令牌，三端完全通用** |
| `1&_device` | ✅ | 三端格式不同，但都是本地可造：`win32&<uuid>&4.0.15` / `android&<uuid>&9.4.52` |
| `x-tk` | ✅ | 用 device_id + uid 本地签，算法有真机金标逐字节回归 |

实验脚本 `tools/reverse/test_universal_cookie.py:1-10` 的设计意图写得很直白：「拿网页账号的 `1&_token`，按 App 格式造一套 Cookie（随机 uuid + 本地签 x-tk），去打移动版 V4」。README:295-303 记载结论：**自造 device + 本地票 → 移动版 V4 直接返回 5 档地址，且下载付费章节的体积与真机凭证结果一字节不差**。

派生参数与落盘（`auth.py:409-471`）：
- 设备 UUID 持久化在 `~/.ximalaya_device_uuid`（`load_or_make_device_uuid`，`auth.py:357-373`），保证三端用同一台"设备"。
- 落盘三文件：`web_cookie.txt` / `pc_cookie.txt` / `mobile_headers.json`；**写入前把同名非空文件备份成 `.bak`**（源项目注释记载踩过坑：一次 derive 把真机 x-tk 冲掉了）。

### 对本项目的意义

这是用户最关心的能力，且**本项目已具备全部原料**（`ximalaya_local_ticket.py` 的 x-tk 算法与源项目逐字节一致）。真正缺的只是**派生这一层薄逻辑**：

1. 从扫码结果的 `1&_token` 拆出 `(uid, token)`；
2. 生成/读取一个持久化 device UUID；
3. 按三端格式拼 cookie；
4. 调已有的 `generate_mobile_ticket()` 出 x-tk；
5. 接进 AudioFlow 的凭证存储（`core/cookie_manager.py` / `ximalaya_credentials.py`）。

**风险点**：必须沿用源项目的「写前备份」与「不覆盖真机抓包」策略 —— AudioFlow 的凭证体系比源项目复杂（多平台共享 `cookie_manager`），静默覆盖用户手抓凭证的后果更重。

## 三、P1-3：移动端 V2 解密常量 + 三密钥兜底链

### 现状对比（本次逐个常量比对）

| 密钥 | 源项目 | AudioFlow | 结论 |
|---|---|---|---|
| web AES（`aaad3e4f…bf93`） | `crypto.py:173` | `ximalaya_manager.py:476`、`download_manager.py:1463,2743` | ✅ **已重合** |
| 移动 V4 签名 key（`9e3B103b…12E3`） | `crypto.py:190` | `download_manager.py:84` | ✅ **已重合** |
| 签名后缀（`0zpnlXAG`） | `crypto.py:192` | `download_manager.py:86` | ✅ **已重合** |
| 移动 V0/V1 解地址 key（`5776f21b…f16a`） | `crypto.py:194` | `download_manager.py:183,1323` | ✅ **已重合** |
| XUID_KEY / TICKET_KEY | `crypto.py:218-221` | `ximalaya_local_ticket.py:26-31` | ✅ **逐字节相同** |
| **移动 V2 的 `V2_XOR_KEY` / `V2_SUBST`** | `crypto.py:205-215` | 有同构算法但**常量不同** | ⚠️ **互补，可新增兜底** |
| PC mac/win 签名 key | `crypto.py:177-184` | — | ❌ 缺（P0-1 一并搬） |
| `SESSION_AES_KEY` | `sign.py:64` | — | ❌ 缺（P0-1 一并搬） |

**关于 V2**：AudioFlow 的 `_decrypt_audio_url_xor`（`ximalaya_manager.py:497-537`）用的 `key_www2`/`sbox_www2` 与源项目的 `V2_XOR_KEY`/`V2_SUBST` **不同**，但两者算法结构完全同构：

```
源项目 V2 :  plain[i] = V2_SUBST[payload[i]] ^ V2_XOR_KEY[i%32] ^ dynamic_key[i%16]
AudioFlow :  data[i] = sbox_www2[data[i]]; ^= iv[i%16]（每16字节）; ^= audio_key[i%32]（每32字节）
```

这大概率是**同一算法的两个渠道变体**（www2 渠道 vs android V2 渠道）。因此两边常量是**互补关系而非重复**：把源项目那套加进你的兜底链，可以多覆盖一类密文。

源项目的兜底链设计值得照搬（`crypto.py:333-367`）：
- `decrypt_mobile_any(encoded, order=("v2","v1","v0"))` —— 依次试，每次结果都必须通过 `looks_like_cdn_url()` 校验才认；
- `decrypt_url_any()` —— 终极兜底：web ECB → mobile V0/V1 → mobile V2；
- `looks_like_cdn_url()`（`crypto.py:286-291`）要求 **http(s) 前缀 + CDN 域名（xmcdn/ximalaya）+ 路径后缀（.mp3/.m4a/.flac…）三重命中**，防止把乱码误判成地址。

AudioFlow 已有等价的 `_is_valid_cdn_url`（`ximalaya_manager.py:457-463`），思路一致，无需替换。

## 四、P1-4：可直接吸收的实测工程结论（零成本）

以下都是源项目**实测**得出、且能直接改善 AudioFlow 的知识点，多数不需要改架构：

### 4.1 静默失效类（最值钱）

| 结论 | 证据 | 对本项目的动作 |
|---|---|---|
| **本地票据其实可用** —— 源报告原称"纯 Python 票据 V4 恒 1001"，实测被推翻。真因有二：① 业务标识必须是 `b=playTrack&s=play`，而不是 `default/default`；② 票据**会过期**（31.9 天前的真机票恒 1001，同 device 现签立刻 200） | `ticket.py:4-10` vs README:248-256 | 检查 `ximalaya_local_ticket.py` 的默认 business/scene 是否为 `playTrack`/`play` —— 它当前默认值正确（`:90`），但值得确认上层调用没有传 `default` |
| **字段名误导**：`playPathAacv224` → 实际 **24K**（不是 224k）；`playPathAacv164`/`playUrl64`/`downloadUrl`/`downloadAacUrl` → 实际 **48K**（不是 64k）；`playPathHq` **地址字段根本不存在**，只有 `playHqSize`，96K 需自行拼 `/3` | 源「下载接口分析.md」L77-80；`source_web.py:32-37` | 核对 `ximalaya_manager.py:118-127` 的 `ui_quality_mapping` 是否按字段名推码率 |
| **集列表要匿名请求** —— 带 App Cookie 反而 `ret=924 该内容因故已下架` | `source_mobile.py:156-164` | ⚠️ **与 AudioFlow 的现有做法相反**（`ximalaya_manager.py:1371`「优先使用移动端 App 凭证绕过专辑级 924」、`:1432`「此前漏带 Cookie」）。两者可能针对不同接口（源项目指 `mobile/v1/album/track`，AudioFlow 指 `revision/album/v1/getTracksList`），**建议实测确认，不要盲目改** |
| **web 端 `baseInfo` 匿名一律 `ret=1001`** | `source_web.py:176-179` | 若本项目有匿名走 web v3 的路径，需确认它在无 Cookie 时是否静默失败 |
| **搜索被风控的识别法**：`ret=0` 但 `albums/tracks` 为空、而 `recommendItems` 有真实数据 → 是被风控扣下，不是参数错 | 源「元数据与搜索接口.md」L41-96 | 可让「搜索无结果」在 UI 上区分"真无结果"与"被风控降级" |
| **`ret=1001` 的多种真因**：缺 `Cookie2: $version=1`、签名带 `%0A`、票据过期、业务标识错、真风控 | 多处 | 本项目对 1001 已有多分支处理，可对照补充归因信息到日志 |
| **缺 `1&_device` → `ret=2004「参数错误，请重新打开App后再尝试」`** | `source_pc.py:15` | 错误提示可更精确 |

### 4.2 参数与档位

- **移动端 level 12/13 必须附 `canPlayDolby=true` / `canPlayVividSound=true`**，否则服务端**静默省略**该档位（不报错，直接不返回）。→ AudioFlow 已实现（`download_manager.py:1143-1145`），✅ 无需动作。
- **降级链最多试 3 档**（`source_mobile.py:293`），避免烧风控；AudioFlow 的 `LEGACY_REDIRECT_LEVELS` 已与源项目实测一致。✅
- 音质档位实测对照（web `redirect/free/play`）：`/0` → ~24.8kbps；`/1` `/2` → **48.8kbps**（`-aacv2-48K.m4a`）；`/3`~`/10` → **96.8kbps 封顶**（96K 即上限，没有 128/320）。→ AudioFlow 已按此修正。✅

### 4.3 反爬与并发

- **并发存在出口连接天花板**：源项目实测出口限 ~12 连接，超出产生大量 502。**8 并发最优（32.9 MB/s）**，全量 2115 集 18.27 GB / 10.4 分钟。
- **502 是限流不是权限**：绝不能在 502 时降档，否则会把网络抖动伪装成"音质不可用"。源项目记录了代价：初版误判导致 **537 集中 31 个文件被静默降级**。→ AudioFlow 已有 `XIMALAYA_TRANSIENT_STATUS`（`download_manager.py:71`），✅ 方向正确。
- **节流算法**（`core/fetch/throttle.py`）：非令牌桶，而是「信号量并发上限 + 最小间隔 + 抖动 + 指数冷却 + 渐进恢复」：`min_interval=0.25`、`jitter=0.05`、`concurrency=2`、`cooldown = min(3600, 60*2^(fail_streak-3))`、**连续 24 次成功后间隔 ×0.8 渐进恢复**。其中「渐进恢复」这一条 AudioFlow 可对照自查。
- **移动端二级冷却**：连续 <3 次只锁单个 device 分支 `3.0*n` 秒，≥3 次才全局冷却（`source_mobile.py:269-279`）—— 这个"精准打击而非全局熔断"的设计值得借鉴。

### 4.4 校验与体检

- **用文件头魔数判容器，不信 URL 后缀与 Content-Type**；容器深判需**头尾各读 1MB**（`ftyp` 的 `moov` 常在尾部），从 `stsd` 的 fourcc 映射 `ec-3`→dolby-ec3、`av3a`→audio-vivid、`mp4a`→m4a（`core/media/inspect.py:54-63`）。
- **真实码率反算**：WAV 用 `fmt.byteRate`；FLAC 读 STREAMINFO 总采样/采样率；其余用 `mvhd` 时长算 `size×8/dur/1000`（`inspect.py:185`）。
- **先写 `.part` 再 `os.replace` 原子改名**（AudioFlow 已有）。
- **长度校验**：源项目用**精确比对**（`got != expected` 即删文件抛 `TransientError`），并据此发现**2 集被 CDN 静默截断**（本地 4.95MB / 服务端 16.80MB，"连接提前 EOF 却不抛异常"）。→ AudioFlow 部分路径用 80% 容差（旧分析 P1-6 提过），可对照确认是否已统一。
- **解密结果必须过 CDN 形态校验**，否则乱码会被当成功。
- **`safe_name`**：`[\\/:*?"<>|\r\n\t]` → `_`、空白折叠、去尾点、截 120 字符。

## 十、网页版无损（FHQ）修复与 UI 适配

> 实施日期：2026-09-26　|　52 项新测试 + 全量回归通过

### 10.1 诊断结论：是同一个接口，但无损在选择阶段被丢弃

两边调用的完全是同一个接口：

```
GET https://{host}.ximalaya.com/mobile-playpage/track/v3/baseInfo/{毫秒时间戳}
    ?device=web&trackId={id}&trackQualityLevel={n}
```

解密也相同：AES-128-ECB + PKCS7，密钥 `aaad3e4fd540b0f79dca95606e72bf93`。

**根因在 `core/ximalaya_download_manager.py:_select_web_play_candidate`**：

```python
# 修复前
preferred_format = 2 if any(marker in upper_type for marker in ("M4A", "AAC")) else 1
candidates.append(((preferred_format, quality_level, expected_size), ...))
_, audio_url, ... = max(candidates, key=lambda item: item[0])
```

`FHQ` 不含 "M4A"/"AAC" → 得 1 分；`M4A_128` → 得 2 分。`max()` 先比第一项，
**M4A_128 永远胜出**。所以即使服务端返回了 41,673,076 字节的 24bit WAV 母带，
实际下载的仍是 1,906,367 字节的 M4A_128 —— 差 21 倍。

函数注释 "preferring M4A containers" 就是这个设计意图，它恰好把列表里唯一
比 M4A 更好的东西排除了。

### 10.5 仍需注意

1. **前端需要重新构建**：`frontend/` 未安装 `node_modules`，本次只改了源码与
   语法校验（`node --check` + 集合求值）。上线前需 `npm install && npm run build`。
2. **无损不是每张专辑都有**：取决于内容方是否上架 WAV 母带。源项目抽样
   100+ 音轨 / 60+ 专辑，**存在 FHQ 的极少**（已知《哈利·波特》`68117318` 有；

3. **体积警告**：无损单集 40～300 MB，整张专辑可能达 TB 级，不要盲目全量跑。

## 十一、Cookie 管理 UI 适配（三端通用）

> 实施日期：2026-09-26

### 11.1 结论：需要调整，而且原有一句是**事实错误**

扫码弹窗原文案：

> 喜马拉雅扫码只授权网页会话，不会导出手机 App 请求头；此前单独保存的移动端凭证会保留。

这句话在 P0-2 落地后**与代码行为直接矛盾** —— 扫码现在会自动派生 App 端凭证。
留着它会让用户以为"必须再手工抓包一次"，正好把新能力的价值抹掉。

### 11.2 改动清单

| # | 位置 | 改动 |
|---|---|---|
| 1 | 凭证状态区 | 新增「电脑版」pill：`随网页登录可用` / `需先登录网页版`；`title` 说明设备号与 `xm-sign` 都是本地生成。这样三端状态一目了然 |
| 2 | 扫码弹窗 | 改为「扫码成功后会自动派生电脑版与 App 端凭证（设备号与 x-tk 都在本地生成），无需再手工抓包；已单独保存的移动端凭证会被保留」 |
| 3 | 扫码成功瞬间 | 读取后端已经返回的 `session.extra.universal`，提示「登录成功：已自动派生电脑版与 App 端凭证」，并停留 1.2 秒再关闭弹窗（原来成功后立即关窗，用户看不到任何反馈） |
| 4 | 手工粘贴区说明 | 补充「扫码后 App 端凭证会自动派生，通常无需在这里操作；需要指定实体设备或覆盖时才用」 |
| 5 | 手工区底部提示 | 补充「同一个 `1&_token` 在网页端、电脑版与 App 端通用，扫码一次即覆盖三端；这里手工保存的凭证会覆盖自动派生结果，**删除后不会自动重建**」 |
| 6 | 状态文案 | 后端 `complete` 的 message 由「移动端请求头格式完整」改为「移动端凭证已就绪」（原措辞只贴合抓包场景）；pill 的「格式完整」同步改为「已就绪」 |

### 11.3 扫码一次后的 UI 表现

```
网页登录：已设置 │ 电脑版：随网页登录可用 │ 移动版 V4：本地出票就绪
```

三个 pill 全部点亮，用户能直接看出「三端已经就绪」，不必再去猜要不要抓包。

### 11.4 没有改的部分（以及原因）

- **后端 `/api/cookies` 不需要改**：它本来就返回 `has_web_cookie` /
  `has_mobile_ticket` / `mobile_credential`，本次只是把这些字段用起来。
- **新增的「电脑版」pill 直接复用 `has_web_cookie`**：PC 通道只需要网页登录态
  （`1&_device` 与 `xm-sign` 全在本地生成），单独维护一个后端状态字段是多余的。
- **手机号验证码登录（Bridge 路线）保留**：文案与扫码路线不冲突，且它是
  没有网页登录态时的另一条路。

### 11.5 扫码成功后的三端摘要面板

只弹一句「登录成功」不够直观，因此扫码成功时会在二维码下方展开一个摘要面板，
数据直接来自后端已返回的 `session.extra.universal`（即 `bundle_summary()`）：

```
网页端：已就绪 │ 电脑版：已就绪 │ App 端：已就绪
账号 uid 276860626 · 设备 73464970…
```

- 三端各自按真实字段判定：网页端看 `web_cookie_ready`；电脑版看
  `pc_cookie_ready && pc_device_present`；App 端看 `mobile_cookie_ready && ticket_ready`。
  未就绪的项显示为黄色 `warning` pill，而不是一律显示成功。
- 设备 UUID 只显示前 8 位，避免把完整设备号摊在界面上。
- 弹窗停留时间从 1.2 秒延长到 2.6 秒，够看清三项状态。
- **零新增 CSS**：直接复用凭证区已有的 `.xmly-credential-status` /
  `.xmly-credential-pill` 样式（`desktop.css:982-985`、`mobile.css:723-726` 都有定义）。
